# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A collection of [SilverBullet](https://silverbullet.md) libraries written in Space-Lua. A "library" here is **not** a plug/JS bundle: it is a single markdown page that a user installs into their SilverBullet space via the Library Manager, containing documentation plus one ` ```space-lua ` code block. The only library so far is `kanboard` (SilverBullet ↔ Kanboard task sync).

Users install from `REPO.md` (the repository index, consumed as a raw GitHub URL), which points at `releases/Kanboard.md`.

## Build / test / release

Everything goes through the Makefile (`make help` lists targets). Env overrides come from `.env` (gitignored — copy `.env.example`).

```sh
make            # = make help
make build      # concatenate src/kanboard/* -> test/build/Kanboard.md
make testspace  # build + assemble test/test/ space and generate its CONFIG.md from .env
make test       # build + testspace + run SilverBullet in Docker on $SB_HOST_PORT, open browser
make clean      # kill the container, rm -rf test/build test/test
make bump-fix / bump-feature   # edit RELEASE_PATCH / RELEASE_MINOR files
make release    # copy build to releases/Kanboard.md, write releases/VERSION, git tag vX.Y.Z
```

There is **no automated test suite and no linter** — "testing" means `make test` and exercising the commands by hand inside the SilverBullet UI. Because the library only exists as generated markdown, always `make build` (or `make test`) after editing `src/` and never edit the generated artifacts.

`make release` refuses to run if `releases/VERSION` already equals the current `RELEASE_MAJOR.MINOR.PATCH`, so bump first.

### Generated files — do not edit

- `test/build/Kanboard.md`, `test/test/**` — gitignored build output
- `releases/Kanboard.md`, `releases/VERSION` — committed, but only ever written by `make release`

## Source layout and assembly order

`make kanboard` concatenates, in this exact order, into one page:

1. `src/kanboard/frontmatter.md` — page frontmatter (`name: Library/Finestream/Kanboard`, `tags: meta/library`)
2. an autogenerated "do not edit" note
3. `src/kanboard/kanboard.md` — user-facing docs (features, config reference, command list); ends with a `## Code` heading that the code block falls under
4. `src/kanboard/library.lua` then `src/kanboard/kanboard.lua`, wrapped in a single ` ```space-lua ` fence

Consequences: `library.lua` is loaded before `kanboard.lua`, so `Kanboard.*` may call `Library.*` freely; both share one global Lua scope; and any user-visible change must be documented in `kanboard.md` in the same edit, since that file *is* the library's documentation.

`Library` (in `library.lua`) is the generic, Kanboard-agnostic layer: UUIDs, frontmatter read/write, "subtree" and "current task" extraction, page creation, plus the `pageId:` virtual page and `/idea`. `Kanboard` (in `kanboard.lua`) is the integration layer. Keep new reusable editor/page helpers in `Library`.

Empty `kanboard/` and `scripts/` directories at the repo root are vestigial.

## Kanboard integration architecture

**Transport.** All Kanboard access goes through `Kanboard.rpc(method, params)` → JSON-RPC POST to `<kbBaseUrl>/jsonrpc.php` via `net.proxyFetch` with Basic auth from `kbUsername`/`kbToken`. Every call site checks `Kanboard.checkResponse(response)` (which also emits debug notifications when `config.get("kanboard").debug` is set) and bails with `editor.flashNotification(..., "error")` on failure. Follow that pattern rather than inventing new error handling.

**Config** lives in the user's `CONFIG` page under the `kanboard` key, read with `config.get("kanboard")`: `kbBaseUrl`, `sbBaseUrl`, `kbUsername`, `kbToken`, `kbProjectId` (default project), `sbCachePath`, `sbCacheRefreshHours`, `kbCloseDone`, `kbMoveDone`, plus optional `debug`. `make testspace` generates an equivalent CONFIG.md from the `KB_*`/`SB_*` env vars, so a new config key must be added in three places: `kanboard.md` docs, the `testspace` target, and `.env.example` if it should be settable per-developer.

**The cache is the data model.** Kanboard is the source of truth; SilverBullet holds a mirror as ordinary markdown pages at `<sbCachePath>/<projectId>`, tagged `KanboardManaged`. Each Kanboard task becomes one SilverBullet task line built by `Kanboard.buildCacheEntry` — the single point of maintenance for the cache format:

```
* [ ] Title ([KB](url)) #<tag> #<category-Name> [kbId: 42] [column: Doing] [projectId: 2] [due: …] [swimlaneId: …] [pageId: …]
```

Those bracketed attributes are what SilverBullet's indexer exposes, so all lookups are `query [[from index.tasks() where kbId == … ]]`-style queries over the cache — never RPC calls. Changing an attribute name silently breaks every query in `kanboard.md`, the slash commands, and users' pages. Angle brackets are stripped from tags/category names (`Library.escapePattern`) because they cannot be escaped in SilverBullet tags.

**Cache refresh** (`Kanboard.updateCache(projectId, kbTask)`) is deliberately two-mode: with no cache page, a stale one (`lastSync` older than `sbCacheRefreshHours`), or no `kbTask`, it does a full `rebuildCache` (one `getAllTasks` call); otherwise `updateCacheEntry` rewrites just that task's line in place. Keep both paths working. Note `buildCacheEntry` still issues one `getTaskTags` RPC per task, so rebuilds are O(tasks) round trips.

**Page identity.** Pages get a `pageId` UUID in frontmatter; Kanboard tasks store it in their `reference` field and get an external link to `<sbBaseUrl>/pageId:<uuid>`. The `virtualPage` handler for `pageId:(.+)` resolves that back to a page and navigates, so links survive page renames. Never key anything off page names.

**Round trip.** `Kanboard: Send Task` (`Ctrl-Alt-a` / `Ctrl-Cmd-a` on mac) takes the task under the cursor, creates it in Kanboard, then *replaces the source line with a live query* (`Kanboard.queryTask`) that renders the cached copy — so after sending, the page no longer owns the task text. Project/swimlane come from page frontmatter (`kbProjectId`, `kbSwimlaneId`) falling back to config. `Kanboard: Sync Status` pushes locally-completed tasks back (close and/or move to the last column per `kbCloseDone`/`kbMoveDone`), and `Kanboard: Remove Cache` deletes all `KanboardManaged` pages after an `editor.confirm`.

## Conventions

- Lua indented with **tabs**; every function and every `command.define`/`slashCommand.define`/`virtualPage.define` is preceded by a 71-dash banner comment documenting behaviour, returns, and workflow steps. Match this — it is the only documentation of the API surface.
- Commands are named `"Kanboard: <Title Case>"`; slash commands are lowerCamelCase.
- SilverBullet globals (`config`, `net`, `encoding`, `editor`, `query`, `space`, `command`, `slashCommand`, `virtualPage`, `js`, `yaml`) are declared in `.vscode/settings.json` under `Lua.diagnostics.globals` — add new ones there when used. That file is gitignored, so it may be absent in a fresh clone.
- Commit messages use informal prefixes seen in history (`Feature ...`, `bug fix: ...`, `Cosmetic: ...`, `Refactoring ...`).
